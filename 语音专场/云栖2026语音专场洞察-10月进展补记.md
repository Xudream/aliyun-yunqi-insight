## 1. 一句话进展

模型这一代没有换代（仍是 9/22 发布的 Qwen-Audio-3.1 家族），但这一个月发生了三件足以改判断的事：

1. **API 侧全部落地并公开定价**：Realtime 正式型号 `qwen-audio-3.1-realtime-plus` 上架，ASR 五款、TTS-Next 全部进模型列表
2. **运行时侧换代**：`qwen-audio-agent` 从 v1.11 跳到 **v2.0.0**（重写编排层），并发布技术报告
3. **技术报告把"端到端实时模型怎么和后台 Agent 配合"讲清楚了**：arXiv:2609.25176 给出 Think / Act / Speak & Coordinate 三支柱与双分支架构，以及一组可对标的数字

### 1.1 三条最重要的事实

| # | 事实 | 为什么重要 |
|---|---|---|
| 1 | Realtime 技术报告公开了**双分支架构**（全双工决策分支 + 内容生成分支，同构 Audio Encoder + LLM） | 说明"什么时候说"和"说什么"在架构层面就是分开的，我们自研 VadJudge 的方向有厂商一手证据 |

> 最后一条等于官方把"语义 VAD + 目标说话人锁定"做成了 API 参数。我们的自研语义 VAD 如果要保留差异化，卖点不能只是"能判附和声"。

## 3. 语言与方言支持（问题 1）

这一节回答"ASR、TTS 增加支持语言的数量（包括方言）"。三份官方文档给的其实是**同一张中文方言清单**，差别在外语覆盖。

### 3.1 ASR：30 语种 + 7 大方言 + 9 类官话口音

`qwen-audio-3.1-asr-flash-message`、`-streaming`、`-filetrans`、`qwen-audio-3.1-asr-flash` 以及 `fun-asr-realtime` 主版本，语言表完全一致【官方文档】：

| 维度 | 覆盖 |
|---|---|
| 外语 | 29 种：英、日、韩、越南、泰、印尼、马来、菲律宾、印地、阿拉伯、法、德、西班牙、葡萄牙、俄、意大利、荷兰、瑞典、丹麦、芬兰、挪威、希腊、波兰、捷克、匈牙利、罗马尼亚、保加利亚、克罗地亚、斯洛伐克 |
| 中文方言 | 7 种：粤语、吴语、闽南语、客家话、赣语、湘语、晋语（+普通话） |
| 官话口音 | 9 类分区：中原、西南、冀鲁、江淮、兰银、胶辽、东北、北京、港台 |
| 口音到地区 | 18 个地区：河南、陕西、湖北、四川、重庆、云南、贵州、广东、广西、河北、天津、山东、安徽、南京、江苏、杭州、甘肃、宁夏 |
| 合计口径 | **30 语种**（中文 + 29 外语），中文含 8 种变体 |

代际对比（同样是官方文档）：

| 代际 | 语种数 | 中文变体 | 备注 |
|---|---|---|---|
| Qwen3-ASR（`qwen3-asr-flash*`） | 26（中文 + 25 外语） | 5（普通话 + 四川话、闽南语、吴语、粤语） | 含土耳其语、乌克兰语、冰岛语等 Audio-3.1 未列的语种 |
| Qwen-Audio-3.1-ASR | **30** | **8** | 新增粤语体系化覆盖 + 9 类官话口音 |
| Paraformer v2（上一代） | 7 | 19 | 中文方言多但外语少，官方建议迁移 |
| Fun-ASR 版本化快照（`fun-asr-realtime-2026-02-28`） | 3 | 8 | 版本化名称仅中英日，需注意型号差异 |

**结论**：ASR 这代的增量不是"外语更多"（3.1 反而少了土耳其、乌克兰、冰岛三种），而是**中文方言体系化**——从 4 个方言扩到 7 个，并补上"9 类官话口音 + 18 地区"这一层，这在国内普通话不标准的场景里比多几种小语种有用得多。

### 3.2 TTS：16 语种 + 20 种方言（按音色类型分档）

TTS 的语言支持**不能只报一个数**，它按"音色类型"分三档【官方文档】：

| 音色类型 | 语种 | 中文方言 |
|---|---|---|
| 系统音色（Qwen-Audio-TTS 系） | 因模型和音色而异，以音色列表为准 | 部分音色直出方言，部分靠指令控制 |
| 复刻音色 | **16 语种**：中、英、日、韩、俄、法、德、葡、泰、印尼、越、西、意、马来、菲、阿拉伯 | **20 种方言**：广东、重庆、东北、甘肃、贵州、浙江、河北、河南、湖北、湖南、江西、宁波、宁夏、青岛、陕西、山西、山东、上海、四川、云南（+普通话共 21 变体），通过指令控制设置 |
| 设计音色 | 2：中文（普通话）、英文 | 不支持 |
| Qwen-Audio-3.1-TTS-Next | 2：中文、英文 | Audiogen 定位（人声+音效+环境音），非流式 |

对照参考（同期 CosyVoice v3-flash 系统音色）：中文 10 变体（普通话 + 广东、东北、河南、湖南、陕西、山东、四川、安徽、闽南）+ 英日韩印尼。

**结论**：TTS 的方言能力这代从"只能用指令控制"走到"系统音色直出 + 指令控制"两条路并存，但**设计音色与 TTS-Next 都不支持方言**——做方言产品必须锁定"复刻音色"这条路径。

### 3.3 Realtime：14 语种 + 20 种方言

| 代际 | 语种 | 中文方言 |
|---|---|---|
| `qwen-audio-3.1-realtime-plus` / `-flash` | **14**：德、英、西、法、印尼、意、日、韩、葡、俄、中、泰、越南、阿拉伯 | 普通话 + 20 种方言（同上清单） |
| `qwen-audio-3.0-realtime-plus` / `-flash` | 11：缺泰语、越南语、阿拉伯语 | 同上 |

另外 Realtime 支持分别指定输入源语种（`session.input_audio_transcription.language`）与输出目标语种（`session.output_audio.language`），但官方明确"输出语种会尽可能生效，不保证，也不改变回复文本的语种"【官方文档】。

### 3.4 三张语言表放在一起看

| 能力 | ASR | TTS（复刻音色） | Realtime |
|---|---|---|---|
| 外语语种 | 29 | 15 | 13 |
| 中文方言 | 7 大方言 + 9 类官话口音 | 20 | 20 |

## 4. Realtime 技术报告读解

来源：**arXiv:2609.25176**《Qwen-Audio-3.1-Realtime: Towards Reliable Agentic Voice Interaction》v1（2026-09-21）/ v2（2026-09-24），署名 Alibaba Token Foundry【论文】。

### 4.1 双分支架构：决策分支 + 内容分支 + 渲染器

这是"祝博提到的双分支"在论文里的原文结构（§2.1、Figure 3）：

| 组件 | 输入 | 输出 | 作用 |
|---|---|---|---|
| 全双工决策模型（分支一） | 流式音频 | **继续听 / 开始说 / 停止 / 打断后恢复** 四选一 | 控制说话时机，不看内容 |
| 语音转文本模型（分支二） | 流式音频 | 回复内容（文本） | 决定说什么 |
| 上下文感知渲染器 | 内容 + 对话历史 + 语音线索 + 声学上下文 | 流式语音 | 用决策信号控制语音起停 |

两条分支**同构**：都是 Audio Encoder + LLM。报告特别强调 `Listen` 与 `Think` 支持 `Act` 与 `Speak` **并发**——工具执行期间可以播报进度（这正好是我们垫词/进度播报的架构依据）。

### 4.2 三支柱训练

| 支柱 | 做法 | 解决的问题 |
|---|---|---|
| **Think** | Core-Cocktail 监督微调 + 多模态/多教师在线策略蒸馏（M²-OPD），把语言能力迁移进音频策略 | 音频侧缺语言推理能力 |
| **Act** | 自进化可执行环境 + 多粒度 rollout + GRPO（对话级/里程碑级/轮次级三级奖励） | 工具调用与任务完成 |
| **Speak & Coordinate** | 对齐"说不说 / 何时说 / 怎么说"，§5.1 划权限边界，§5.2 给出决策策略 π(o≤t, h≤t, s_t) | 该沉默时沉默、该等待时等待 |

两条设计原则值得单独记：

- **"口头承诺既不是执行证据，也不是授权令牌"**（§5.1）——模型说"已完成"不等于真的完成，权限由运行时和工具强制
- 决策策略的输入包含**当前系统状态**（是否正在播报、是否正在执行工具），动作空间含"打断后恢复"（§5.2）

### 4.3 关键数字

| 指标 | 3.0 | 3.1 | 变化 | 口径 |
|---|---|---|---|---|
| τ-Voice 任务成功率（半双工 S2T 适配版） | 78.4% | **82.0%** | +3.6pt | 不可与官方全双工 S2S 直接比 |
| ├ Retail / Airline / Telecom | 72.8 / 64.0 / 90.4 | 73.7 / 74.0 / 93.9 | 航空 +10pt 最明显 | 同上 |
| Full-Duplex-Bench v1.5 对背景语音响应率 | 73.0% | **13.0%** | **-60pt** | S2S，越低越好 |
| FLEURS WER（14 语种宏平均） | 9.01 | **3.98** | -5.03 | 越低越好 |
| Audio MultiChallenge（AMC） | 47.12 | **52.21** | +5.09pt | 自建裁判口径偏差 |
| SpeechFCEval（语音函数调用） | 83.28 | **86.00** | +2.72pt | 官方基准 |
| WebSearch1K 平均生成查询数 | 4.37 | **1.05** | **-76%** | 自建集 |
| Big Bench Audio（BBA） | 98.80 | 98.50 | -0.30pt | 基本持平 |

佐证：普通音频理解与长上下文也在涨——LongBench v2 +6.76pt、MiniLongBench +4.40pt、Long-AMC +8.04pt；人格/共情 8 项里 3.1 全面高于 3.0（真实人声共情集 4.37→4.74，满分 5）。

### 4.4 报告自己承认的边界（必须一起引用）

- 多数为**描述性对比**，无置信区间、无重复种子、无污染分析、无组件消融
- τ-Voice 用的是**半双工 S2T 适配**，不是官方全双工 S2S 协议
- **持久任务（前后台协调、任务生命周期、结果回传）的证据来自独立 Voice Harness 原型，且前台用的是 3.0**；报告明确写"3.1 模型的端到端评测与正式异步生命周期仍是开放问题"
- 未评估长时程可执行语音任务、也缺大规模人工红队

> 这三条决定了我们对外的说法：**"端到端 + 后台 Agent"是经过原型验证的工程路径，不是已经产品化的既定结论。**

## 5. 端到端 vs 级联

### 5.1 大厂路线盘点

| 厂商 | 实时交互路线 | 形态 | 证据 |
|---|---|---|---|
| OpenAI | GPT-Realtime-2 | 端到端 S2S | 作为基线出现在 3.1 技术报告 Table 2/8 |
| Google | Gemini Live（含 3.7 Flash 档） | 端到端 S2S，支持视频输入 | 报告 Table 4 基线 + qwen-audio-agent 前端支持 |
| 阿里 | Qwen-Audio-3.x-Realtime、Qwen3.5-Omni Realtime、Qwen3.8 Omni Flash Realtime | 端到端，双分支 | 官方文档 + 技术报告 |
| 字节 | Seeduplex 1.2.6.1 / 3.0 Realtime | 端到端全双工 | 报告基线 + qwen-audio-agent 前端支持 |
| 阿里（执行侧） | Voice Harness：前台 Realtime + 后台文本 Agent | **级联** | 报告 §7 + qwen-audio-agent v2 |

**判断（可对外讲的核心观点）**：

> 一线厂商的**交互入口已经全面端到端化**，"干活"这一层反而回到了文本 Agent。也就是说趋势不是"端到端取代级联"，而是**分工固定下来：端到端负责说，级联负责做**。

三条支撑理由：

1. **时延结构不同**：级联的时延是 ASR 判停 + LLM 首 token + TTS 首包三段相加；端到端把判停与首包压在同一模型内，且打断/抢话不必等 ASR 出字
2. **能力取向不同**：工具调用、长任务、记忆、审计要的是**结构化文本与可回放轨迹**，端到端语音模型在 2026 年仍靠外挂 Harness 补（报告 §7 用文本后台执行器就是这个证据）
3. **工程可运维性不同**：级联每一段都能单独埋点、单独换、单独回放；端到端出错只能整段重训

### 5.2 优势对比

| 维度 | 级联（ASR → LLM → TTS） | 端到端（Realtime S2S） |
|---|---|---|
| 首响应时延 | 三段串联，判停必须等 ASR | 单模型内完成，可边听边判 |
| 打断与抢话 | 依赖外挂 VAD + 规则，易误打断 | 决策分支原生输出"停止/恢复" |
| 副语言（情绪、语气、笑声） | 文本链路丢失 | 保留，可模仿 |
| sidetalk / 旁人语音 | 靠独立拒识模型，F1 上限约 0.86（单通道） | 训练后可到"背景语音响应率 13%"量级 |
| 工具调用 / 长任务 | 天然适配，可回放可审计 | 需 Harness 外挂补 |
| 可调试性 | 每段可埋点、可替换 | 黑盒，只能端到端重训 |
| 成本结构 | 分段计费，通常更低 | 按音频 token 计费，实时流更贵 |
| 数据门槛 | 各段可独立买/开源 | 需万小时级真实双工数据 + 流式训练栈 |
| 幻觉控制 | 文本侧可约束解码 | 语音侧难约束，易"自信地胡说" |
| 方言/语种 | 各段独立选型 | 受模型整体覆盖限制 |

### 5.3 对我们四层架构的结论

我们的 L1（语音交互）/L2（路由）/L3（小脑）/L4（大脑）分层，与"端到端做说、级联做做"是一一对应的：

| 我们的层 | 该用哪种 | 理由 |
|---|---|---|
| L1 语音交互 | **两种都留**：端到端 Realtime 做自然对话；级联保留 ASR/TTS 做可控场景与私有化 | 端到端赢在打断与时延，级联赢在可控与方言/合规 |
| L2 意图路由 | 级联（文本） | 路由需要结构化输入与可解释判据 |
| L3 小脑 | 级联（文本 LLM） | 承接语、转述、工具调用都要可约束、可评测 |
| L4 大脑 | 级联（文本 Agent） | 与厂商做法一致（报告的后台执行器就是文本 Agent） |

## 6. 我们要不要自建 Realtime 模型

### 6.1 三个台阶

| 台阶 | 内容 | 训练成本 | 能力收益 |
|---|---|---|---|
| **L0 纯 API** | 直接调 `qwen-audio-3.1-realtime-plus` | 0 | 立即拿到 14 语种、20 方言、双工与工具调用 |
| **L1 自建"决策分支"** | 只训全双工决策模型（继续听/开始说/停止/恢复）+ 语义 VAD + sidetalk 判定，1–4B 级 | 低：自有对话日志 + 少量标注，LoRA 级即可【估算】 | 差异化全部集中在这里（抢话策略、附和声、旁人语音、方言口音） |
| **L2 全自建端到端** | Audio Encoder + LLM + 渲染器全链路，含 Act（工具）与 Speak（风格） | 高：万小时级双工数据 + 多阶段训练（SFT→OPD→GRPO）【估算】 | 时延与自然度可控，但工程风险最大 |

### 6.2 判断依据

| 问题 | 我们的现状 | 结论 |
|---|---|---|
| 时延是不是硬壁垒？ | 是（端到端 5s→2s 是 Q3 指标） | 支持自建，但 API 也能先达成 |
| 有没有独占数据？ | 有（真实双工对话日志 + sidetalk 场景） | **支持 L1**，这是唯一别人拿不到的资产 |
| 需要私有化/合规？ | 内网场景存在 | 支持级联自研，不必端到端 |
| 方言/口音是卖点？ | 河南等官话口音场景 | 支持 L1（决策分支对声音敏感度低，ASR 用云 API 即可） |
| 有流式训练栈与多卡资源？ | 目前无 | **不支持 L2** |

### 6.3 建议

**先做 L1，明确不做 L2。** 三条理由：

1. 我们真正的差异化在"什么时候说、说不说"（抢话、附和、旁人语音、任务等待），这些恰好是**决策分支**的职责，而不是声学生成能力
2. 决策分支的数据可以从自有对话日志自动构造（回合边界、打断点、沉默区间都有时间戳），不需要万小时录音
3. 厂商报告自己承认：端到端模型的"持久任务"能力仍靠外部 Harness 补——也就是说**胜负手在编排层，不在声学层**

启动 L2 的三个前提（任一不满足就不做）：① 端到端时延成为签单硬指标；② 有 ≥5,000 小时自有双工数据；③ 具备 32 卡以上训练与流式推理团队。【估算口径】

### 6.4 成本与风险

| 项 | L1 决策分支【估算】 | L2 端到端【估算】 |
|---|---|---|
| 数据 | 50–200 小时标注 + 全量日志弱标注 | 5,000 小时以上，含噪声/重叠/旁路语音 |
| 训练 | 4B 级 LoRA，8 卡数天 | 9B 级多阶段，32–64 卡数周 |
| 推理 | 单卡可跑，决策延迟 <100ms 量级 | 多卡流式，需自建音频网关 |
| 主要风险 | 与厂商 API 的 smart_turn 功能重叠 | 训练不稳定、幻觉难控、迭代周期以月计 |

## 7. 双分支与 RSI 要不要写进洞察

### 7.1 双分支：必写

三个理由：

1. 它是"**决策与生成解耦**"的一手架构证据（§2.1 原文：两条同构 Audio Encoder + LLM 路径，一条管时机、一条管内容），与我们自研 VadJudge 的思路同源
2. 它给了"垫词/进度播报"一个合法位置：报告明确说 Listen/Think 支持 Act 与 Speak 并发，工具执行期间可以播报进度
3. 它是回应"要不要自建 Realtime"的关键：自建只需要造决策分支，不必造整条链路

**放置建议**：Realtime 章节新增"架构"小节，配一张三分支图（决策分支 / 内容分支 / 渲染器 + 决策控制起停），图下注明出处 arXiv:2609.25176 图 3。

### 7.2 RSI：写，但只写一段并降级

| 项 | 内容 | 口径 |
|---|---|---|
| 是什么 | 递归自我改进（Recursive Self-Improvement）：模型参与自己的训练、推理与芯模协同 | 云栖主论坛 |
| 已有数据 | 连续运行一个月、33 轮有效迭代、人类零参与；吞吐 +96%；EDA 面积 -42%；Qwen3.8-Max 评分 40→45 | **阿里自报，无第三方复测** |
| 路线图 | Qwen4 已开训，Qwen4.5/Qwen5 计划扩到 5–10T 参数 | 同上 |

**为什么降级**：它与"语音交互产品怎么设计"只有间接关系。
**但它对我们有一个真实启发**：RSI 的底座是"可执行环境 + 多粒度 rollout + 自动评分"，这套方法我们自己也能用——给 L3 造一个内部可执行环境（订票、查询、日程沙箱），用对话级/里程碑级/轮次级三级奖励做 GRPO。这比"等更强的模型"更有行动价值。

**放置建议**：Realtime 章节末尾一段"厂商能力演进" + 在训练章节引用"三级奖励 + 可执行环境"的做法，不单独成章。
