    4. Realtime 技术报告读解

    来源：arXiv:2609.25176《Qwen-Audio-3.1-Realtime: Towards Reliable Agentic Voice Interaction》v1（2026-09-21）/ v2（2026-09-24），署名 Alibaba Token Foundry【论文】。

    4.1 双分支架构：决策分支 + 内容分支 + 渲染器

    这是"祝博提到的双分支"在论文里的原文结构（§2.1、Figure 3）：

    组件输入输出作用
    全双工决策模型（分支一）流式音频继续听 / 开始说 / 停止 / 打断后恢复 四选一控制说话时机，不看内容
    语音转文本模型（分支二）流式音频回复内容（文本）决定说什么
    上下文感知渲染器内容 + 对话历史 + 语音线索 + 声学上下文流式语音用决策信号控制语音起停

    两条分支同构：都是 Audio Encoder + LLM。报告特别强调 Listen 与 Think 支持 Act 与 Speak 并发——工具执行期间可以播报进度（这正好是我们垫词/进度播报的架构依据）。

    4.2 三支柱训练

    支柱做法解决的问题
    ThinkCore-Cocktail 监督微调 + 多模态/多教师在线策略蒸馏（M²-OPD），把语言能力迁移进音频策略音频侧缺语言推理能力
    Act自进化可执行环境 + 多粒度 rollout + GRPO（对话级/里程碑级/轮次级三级奖励）工具调用与任务完成
    Speak & Coordinate对齐"说不说 / 何时说 / 怎么说"，§5.1 划权限边界，§5.2 给出决策策略 π(o≤t, h≤t, s_t)该沉默时沉默、该等待时等待

    两条设计原则值得单独记：

  • "口头承诺既不是执行证据，也不是授权令牌"（§5.1）——模型说"已完成"不等于真的完成，权限由运行时和工具强制
  • 决策策略的输入包含当前系统状态（是否正在播报、是否正在执行工具），动作空间含"打断后恢复"（§5.2）

    4.4 报告自己承认的边界（必须一起引用）

  • 多数为描述性对比，无置信区间、无重复种子、无污染分析、无组件消融
  • τ-Voice 用的是半双工 S2T 适配，不是官方全双工 S2S 协议
  • 持久任务（前后台协调、任务生命周期、结果回传）的证据来自独立 Voice Harness 原型，且前台用的是 3.0；报告明确写"3.1 模型的端到端评测与正式异步生命周期仍是开放问题"
  • 未评估长时程可执行语音任务、也缺大规模人工红队

    • 这三条决定了我们对外的说法："端到端 + 后台 Agent"是经过原型验证的工程路径，不是已经产品化的既定结论。

    5. 端到端 vs 级联

    5.1 大厂路线盘点

    厂商实时交互路线形态证据
    OpenAIGPT-Realtime-2端到端 S2S作为基线出现在 3.1 技术报告 Table 2/8
    GoogleGemini Live（含 3.7 Flash 档）端到端 S2S，支持视频输入报告 Table 4 基线 + qwen-audio-agent 前端支持
    阿里Qwen-Audio-3.x-Realtime、Qwen3.5-Omni Realtime、Qwen3.8 Omni Flash Realtime端到端，双分支官方文档 + 技术报告
    字节Seeduplex 1.2.6.1 / 3.0 Realtime端到端全双工报告基线 + qwen-audio-agent 前端支持
    阿里（执行侧）Voice Harness：前台 Realtime + 后台文本 Agent级联报告 §7 + qwen-audio-agent v2

    判断（可对外讲的核心观点）：

    一线厂商的交互入口已经全面端到端化，"干活"这一层反而回到了文本 Agent。也就是说趋势不是"端到端取代级联"，而是分工固定下来：端到端负责说，级联负责做。

    三条支撑理由：

  • 时延结构不同：级联的时延是 ASR 判停 + LLM 首 token + TTS 首包三段相加；端到端把判停与首包压在同一模型内，且打断/抢话不必等 ASR 出字
  • 能力取向不同：工具调用、长任务、记忆、审计要的是结构化文本与可回放轨迹，端到端语音模型在 2026 年仍靠外挂 Harness 补（报告 §7 用文本后台执行器就是这个证据）
  • 工程可运维性不同：级联每一段都能单独埋点、单独换、单独回放；端到端出错只能整段重训

    • 5.2 优势对比

    维度级联（ASR → LLM → TTS）端到端（Realtime S2S）
    首响应时延三段串联，判停必须等 ASR单模型内完成，可边听边判
    打断与抢话依赖外挂 VAD + 规则，易误打断决策分支原生输出"停止/恢复"
    副语言（情绪、语气、笑声）文本链路丢失保留，可模仿
    sidetalk / 旁人语音靠独立拒识模型，F1 上限约 0.86（单通道）训练后可到"背景语音响应率 13%"量级
    工具调用 / 长任务天然适配，可回放可审计需 Harness 外挂补
    可调试性每段可埋点、可替换黑盒，只能端到端重训
    成本结构分段计费，通常更低按音频 token 计费，实时流更贵
    数据门槛各段可独立买/开源需万小时级真实双工数据 + 流式训练栈
    幻觉控制文本侧可约束解码语音侧难约束，易"自信地胡说"
    方言/语种各段独立选型受模型整体覆盖限制

    5.3 对我们四层架构的结论

    我们的 L1（语音交互）/L2（路由）/L3（小脑）/L4（大脑）分层，与"端到端做说、级联做做"是一一对应的：

    我们的层该用哪种理由
    L1 语音交互两种都留：端到端 Realtime 做自然对话；级联保留 ASR/TTS 做可控场景与私有化端到端赢在打断与时延，级联赢在可控与方言/合规
    L2 意图路由级联（文本）路由需要结构化输入与可解释判据
    L3 小脑级联（文本 LLM）承接语、转述、工具调用都要可约束、可评测
    L4 大脑级联（文本 Agent）与厂商做法一致（报告的后台执行器就是文本 Agent）

    6. 我们要不要自建 Realtime 模型

    6.1 三个台阶

    台阶内容训练成本能力收益
    L0 纯 API直接调 qwen-audio-3.1-realtime-plus0立即拿到 14 语种、20 方言、双工与工具调用
    L1 自建"决策分支"只训全双工决策模型（继续听/开始说/停止/恢复）+ 语义 VAD + sidetalk 判定，1–4B 级低：自有对话日志 + 少量标注，LoRA 级即可【估算】差异化全部集中在这里（抢话策略、附和声、旁人语音、方言口音）
    L2 全自建端到端Audio Encoder + LLM + 渲染器全链路，含 Act（工具）与 Speak（风格）高：万小时级双工数据 + 多阶段训练（SFT→OPD→GRPO）【估算】时延与自然度可控，但工程风险最大

    6.2 判断依据

    问题我们的现状结论
    时延是不是硬壁垒？是（端到端 5s→2s 是 Q3 指标）支持自建，但 API 也能先达成
    有没有独占数据？有（真实双工对话日志 + sidetalk 场景）支持 L1，这是唯一别人拿不到的资产
    需要私有化/合规？内网场景存在支持级联自研，不必端到端
    方言/口音是卖点？河南等官话口音场景支持 L1（决策分支对声音敏感度低，ASR 用云 API 即可）
    有流式训练栈与多卡资源？目前无不支持 L2

    6.3 建议

    先做 L1，明确不做 L2。 三条理由：

  • 我们真正的差异化在"什么时候说、说不说"（抢话、附和、旁人语音、任务等待），这些恰好是决策分支的职责，而不是声学生成能力
  • 决策分支的数据可以从自有对话日志自动构造（回合边界、打断点、沉默区间都有时间戳），不需要万小时录音
  • 厂商报告自己承认：端到端模型的"持久任务"能力仍靠外部 Harness 补——也就是说胜负手在编排层，不在声学层

    • 启动 L2 的三个前提（任一不满足就不做）：① 端到端时延成为签单硬指标；② 有 ≥5,000 小时自有双工数据；③ 具备 32 卡以上训练与流式推理团队。【估算口径】

    6.4 成本与风险

    项L1 决策分支【估算】L2 端到端【估算】
    数据50–200 小时标注 + 全量日志弱标注5,000 小时以上，含噪声/重叠/旁路语音

    7. 双分支与 RSI 要不要写进洞察

    7.1 双分支：必写

    三个理由：

  • 它是"决策与生成解耦"的一手架构证据（§2.1 原文：两条同构 Audio Encoder + LLM 路径，一条管时机、一条管内容），与我们自研 VadJudge 的思路同源
  • 它给了"垫词/进度播报"一个合法位置：报告明确说 Listen/Think 支持 Act 与 Speak 并发，工具执行期间可以播报进度
  • 它是回应"要不要自建 Realtime"的关键：自建只需要造决策分支，不必造整条链路

    • 放置建议：Realtime 章节新增"架构"小节，配一张三分支图（决策分支 / 内容分支 / 渲染器 + 决策控制起停），图下注明出处 arXiv:2609.25176 图 3。

    7.2 RSI：写，但只写一段并降级

    项内容口径

    为什么降级：它与"语音交互产品怎么设计"只有间接关系。

    但它对我们有一个真实启发：RSI 的底座是"可执行环境 + 多粒度 rollout + 自动评分"，这套方法我们自己也能用——给 L3 造一个内部可执行环境（订票、查询、日程沙箱），用对话级/里程碑级/轮次级三级奖励做 GRPO。这比"等更强的模型"更有行动价值。
